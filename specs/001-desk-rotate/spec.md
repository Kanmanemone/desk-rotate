## Clarifications

### Session 2026-08-11

- Q: 목표 전환 횟수에 도달하면 프로그램이 어떻게 동작해야 하나요? → A: 전환은 멈추지만 플로팅 창은 열린 채로 최종 통계(총 전환 횟수, 데스크톱별 전환 횟수)를 계속 보여주고, 사용자가 직접 닫아야 종료된다.
- Q: 마지막 데스크톱에 도달했을 때 순환 방식을 어떻게 할까요(끝에서 방향을 바꾸는 핑퐁 방식 vs 처음으로 되돌아가는 순환 방식)? → A: 핑퐁 방식은 양 끝 데스크톱(1번, 마지막 번)이 중간 데스크톱보다 절반만 방문되어 "각 데스크톱을 균일하게 반복 순회"한다는 목적에 어긋나므로 채택하지 않는다. 순환(wrap) 방식을 유지하고, 마지막→처음으로 돌아갈 때 필요한 연속 키 입력 사이에 지연을 두어 입력 씹힘 위험을 완화한다(완전히 제거하지는 못함).
- Q: 전환이 실제로 성공했는지 검증하는 기능을 스펙에 포함할까요? → A: (최초 답변은 "포함하지 않음"이었으나, 이후 재검토를 거쳐 포함하는 것으로 확정됨) 데스크톱마다 창을 하나씩 두고, 공식 `IVirtualDesktopManager.IsWindowOnCurrentVirtualDesktop` API로 전환 시도 후 실제로 도달한 데스크톱을 확인하는 검증 기능을 포함한다. 의도한 데스크톱에 도달하지 못했으면 재시도하고, 그래도 안 되면 실제 위치를 기준으로 내부 상태를 보정한다. 비공식 COM 인터페이스나 강제 포커스 트릭(`SetForegroundWindow` 등)은 쓰지 않는다 — 순수 조회 API라 포그라운드 잠금 문제가 없다.
- Q: 창 상태와 무관하게 전환·검증·카운트 동작이 계속 보장되도록 시스템 트레이 상주 구조를 채택할까요? → A: (최초 답변은 "채택함"이었으나, 이후 재검토를 거쳐 아래 항목으로 대체·확정됨) 트레이 상주 대신, 데스크톱마다 일반 플로팅 창을 두고 사용자가 창을 닫으려 하면 "정말 종료할까요?" 확인을 거치도록 한다. 확인 후 종료를 확정하면 프로그램 전체가 종료된다 — 창이 없으면 정상 동작을 보장할 수 없으므로, 창을 유지하는 것 자체를 확인 절차로 강제하는 방식을 택했다.
- Q: 데스크톱별 창을 hidden 마커 창 대신 일반 플로팅 창으로 바꾸고, 닫을 때 확인 절차를 거치는 방식으로 갈까요? → A: 그렇게 한다. hidden 창과 트레이 상주 대신, 데스크톱마다 사용자 눈에 보이는 플로팅 창(상태 표시와 전환 검증을 겸함)을 두고, 닫으려 하면 확인 창을 띄운다. 확인 후 종료하면 프로그램 전체가 종료되며, 별도의 자동 재생성이나 트레이 메뉴는 필요 없다.
- Q: 프로그램 시작 시 데스크톱 개수만큼 창이 필요한데, 사용자가 이 창들을 직접 각 데스크톱으로 옮겨야 하나요? → A: 아니다. 앱이 시작할 때 각 데스크톱을 자동으로(회전에 쓰는 것과 같은 키 입력 방식으로) 한 번씩 순회하며 방문하는 데스크톱마다 창을 자동으로 생성·배치하고, 끝나면 원래 데스크톱으로 돌아와 평소 회전을 시작한다. 사용자의 수동 개입은 필요 없다. 이 과정에서 화면이 짧게 여러 데스크톱을 오가는 것이 사용자 눈에 보일 수 있다(정상 동작).
- Q: 세션 도중 사용자가 가상 데스크톱의 순서를 바꾸거나 데스크톱을 추가/삭제하면 어떻게 되나요? → A: 시작 시 입력한 개수가 실제와 다른 경우와 동일하게 범위 밖으로 둔다. 기존 검증/재시도/보정(FR-017~019)이 최선의 안전망으로 작동해 극단적으로 어긋나지는 않지만, 순서 변경·추가·삭제에 대한 정교한 재동기화는 보장하지 않는다 — 필요하면 앱을 재시작해 처음부터 다시 설정한다.
- Q: 각 데스크톱의 플로팅 창은 초기에 화면 어디에 위치해야 하나요? → A: 화면 상단 중앙(12시 방향)에 배치한다. 이는 초기 배치일 뿐이며, 이후 사용자는 자유롭게 드래그해서 원하는 위치로 옮길 수 있다.
- Q: (사용자 직접 요청) 순회할 데스크톱을 개수가 아니라 범위(예: 3~7)로 지정하고 싶다 — 1-based로 3,4,5,6,7 데스크톱을 순회하는 식. → A: 반영한다. 시작 데스크톱 번호와 끝 데스크톱 번호(둘 다 1 이상, 끝 ≥ 시작)를 입력받고, 그 범위에 속한 데스크톱만 순회 대상으로 삼는다. 앱은 시작 시 먼저 범위의 시작 데스크톱까지 이동한 뒤(초기 탐색), 기존 초기 설정 과정(FR-020)을 그 범위에 대해 수행한다. 범위의 끝에서 시작으로 되돌아가는 순환 방식은 기존과 동일하게 유지한다(FR-002).
- Q: (사용자 직접 요청) 시작 입력 폼의 기본값을 바꾸고 싶다. → A: 데스크톱 범위 기본값은 1~3, 전환 간격 기본값은 5분(300초)으로 한다.
- Q: (사용자 직접 요청) 플로팅 창이 너무 투박하다 — 테두리 없이 12시 방향에 뜨고, 평소에는 남은 시간 숫자만 딱 보이게, 클릭했을 때만 지금처럼 상세 정보(총 예상 실행 시간, 데스크톱별 전환 횟수 등)가 보이게 해달라. → A: 반영한다. 플로팅 창은 테두리 없는(borderless) 창으로 만들고, 기본 상태(최소 보기)에서는 다음 전환까지 남은 시간(초)만 크게 표시한다. 창을 클릭하면 상세 보기(총 예상 실행 시간, 종료까지 남은 시간, 데스크톱별 전환 횟수)로 전환되며, 다시 클릭하면 최소 보기로 돌아간다. 테두리가 없어 제목 표시줄로 드래그할 수 없으므로, 창 본문을 마우스로 눌러 드래그하는 방식으로 이동을 지원한다(FR-021의 "드래그로 옮길 수 있다"는 요구는 유지, 수단만 바뀜).
- Q: (사용자 직접 요청, 실사용 피드백 4건) ① 목표값을 전환 횟수가 아니라 사이클 횟수(범위 안 데스크톱을 한 번씩 다 훑는 것 = 1사이클)로 입력받고 싶다. ② 상세 보기를 클릭으로 열었을 때 닫을 수단(X 표시)이 없다 — focus 여부에 따라 테두리·닫기 버튼을 동적으로 보여주기 어렵다면 커스텀 닫기 버튼으로 대체해도 된다. ③ 시작 폼에 "초 단위 표시"와 "사이클 번호 표시" 온/오프 옵션을 추가하고, 후자가 켜지면 최소 보기가 "a초" 대신 "[x번째] a초"처럼 표시되게 해달라. ④ 플로팅 창을 화면 테두리 가까이로 드래그하면 (과도하지 않게) 자석처럼 살짝 달라붙게 해달라. → A: 모두 반영한다. (①) FR-013을 목표 사이클 수 입력으로 바꾸고, 시스템이 이를 목표 총 전환 횟수(사이클 수 × 데스크톱 개수)로 환산해 기존 회전·통계 로직에 그대로 사용한다(FR-013, FR-030). (②) focus 상태에 따라 `FormBorderStyle`을 동적으로 바꾸는 방식은 테두리 없는 always-on-top 창에서 깜빡임·위치 튐 등 부작용 위험이 있어 채택하지 않고, 상세 보기에만 작게 커스텀 닫기(×) 버튼을 두어 기존 FR-008 확인 절차로 이어지게 한다(FR-029). 최소 보기는 화면을 가리지 않기 위해 여전히 닫기 버튼을 두지 않는다. (③) 시작 폼에 "초 단위 표시"(기본 켜짐)와 "사이클 번호 표시"(기본 꺼짐) 두 온/오프 옵션을 추가하고, 최소 보기 표시 형식에 반영한다(FR-031). (④) 드래그 중 창이 화면 작업 영역 테두리에서 임계 거리 이내로 들어오면 테두리에 맞춰 자동으로 붙고, 벗어나면 일반 자유 이동으로 돌아가는 자석 스냅을 추가한다 — 임계 거리는 "거의 닿을 수준"으로 작게 잡아 과도한 스냅을 피한다(FR-032).
- Q: (사용자 직접 지적) 범위 입력이 실제로 의미가 있는지 재검토해달라 — 예를 들어 현재 가상 데스크톱이 1개(현재 위치)뿐인데 범위 3~5를 입력하면 어떻게 되는가? 그리고 Windows의 가상 데스크톱 개수에 상한이 있다면 이 프로그램에도 그대로 적용해달라. → A: (범위 유효성) 기존 구현은 초기 탐색·초기 설정에서 전환 키 입력이 항상 성공한다고 가정했는데, 이는 사실이 아니다 — 실제로 존재하지 않는 다음 데스크톱으로의 전환 키 입력은 조용히 무시되며(Windows 표준 동작), 이 경우 서로 다른 범위 번호의 플로팅 창들이 모두 같은 실제 데스크톱 위에 만들어져 전환 검증(FR-017)이 늘 "일치"로 오판하는 심각한 결함으로 이어질 수 있음을 재검토를 통해 확인했다. 이를 해결하기 위해, 초기 탐색·초기 설정의 매 전환 단계마다 공식 API(`IsWindowOnCurrentVirtualDesktop`)로 실제 이동 여부를 확인하고, 이동하지 않았으면(=그 데스크톱이 아직 없으면) Windows 표준 단축키(Win+Ctrl+D, 새 데스크톱 생성+전환)로 새 데스크톱을 만들어 그 자리를 채우도록 한다(FR-033 신설). 이로써 사용자가 입력한 범위는 항상 실제로 존재하는 서로 다른 데스크톱들로 보장된다. (개수 상한) 조사 결과 Windows는 가상 데스크톱 개수에 공식적으로 문서화된 고정 상한을 두지 않으며, 실질적으로 시스템 메모리에 의해서만 제한된다 — 따라서 이 프로그램에 별도의 "OS 유래" 상한값을 적용하지 않는다. 다만 극단적으로 큰 입력으로 인한 대량의 데스크톱 생성을 막기 위해 시작 입력 폼의 범위 시작/끝 입력값 자체는 기존과 같이 1~100으로 제한하는 구현 재량의 안전장치를 유지한다.
- Q: (사용자 직접 요청, 실사용 피드백 2건) ① "사이클 번호 표시" 옵션 기본값을 꺼짐에서 켜짐으로 바꿔달라. ② 심각한 버그 — 이미 여러 데스크톱이 떠 있는 상태에서(예: 4개 존재, 2번째 데스크톱에서 실행) 일부만 겹치는 범위를 입력하면(예: 3~5), 이미 있는 3·4번은 재사용하고 5번만 새로 만들어야 하는데 실제로는 6·7·8·9번처럼 엉뚱하게 여러 개를 새로 만든다. → A: 모두 반영한다. (①) FR-031의 "사이클 번호 표시" 기본값을 켜짐으로 바꾼다. (②) 원인은 초기 탐색(FR-022/FR-033) 구현이 "실행 시점의 데스크톱 = 절대 1번"이라고 잘못 가정했기 때문이다 — 공식 API는 "지금 몇 번째 데스크톱에 있는지" 알려주지 않으므로, 실행 시점이 이미 다른 데스크톱들 사이(예: 4개 중 2번째)에 있으면 범위 시작까지의 이동 칸 수 계산 자체가 틀어져 엉뚱한 위치를 기준으로 부족분을 오판하고 대량으로 새 데스크톱을 만들어버린다. 이를 고쳐, 초기 탐색을 시작하기 전에 먼저 뒤로(Previous) 계속 이동해 더 이상 이동하지 않는 지점(=실제 데스크톱 1번)을 스스로 찾아낸 뒤, 그 지점을 기준으로 범위 시작까지 이동하도록 한다(FR-034 신설). 이렇게 하면 실행 시점이 어디였든 기존 데스크톱을 최대한 재사용하고 부족한 만큼만 새로 생성한다.
- Q: (사용자 직접 지적, 위 FR-034 수정 이후에도 재발) 데스크톱 1번에서 범위 2~3을 입력했는데 1→2로 이동해야 할 것이 1→14처럼 엉뚱하게 먼 데스크톱으로 점프한다. → A: FR-033/FR-034 판정 로직을 진단한 결과, 두 가지 신뢰성 문제를 확인했다. 첫째, 전환 키 입력 직후 공식 API를 딱 한 번만 조회해 "이동했는지"를 판정했는데, 데스크톱 개수가 많아지면 전환 애니메이션이나 조회 자체가 조금 더 걸릴 수 있어 실제로는 이동했는데도 "이동 안 함(=그 데스크톱이 없음)"으로 오판해 불필요하게 새 데스크톱을 만들어버리는 경우가 있었다 — 이 오판이 매 단계 누적되면 엉뚱하게 먼 번호까지 순식간에 만들어질 수 있다. 둘째, 이동 여부 판정에 쓰던 참조 창이 1×1 크기에 완전 투명(Opacity 0)이어서, 화면 구성 요소 합성(DWM)이 이런 극단적으로 작은 창을 건너뛰어 소속 데스크톱 조회 자체가 간헐적으로 부정확할 가능성도 있었다. 두 가지 모두 고쳤다 — (1) 전환 키 입력 후 "이동하지 않은 것처럼" 보이면 곧바로 새 데스크톱을 만들지 않고, 한 번 더 시간을 두고 재확인해 두 번 다 "이동 안 함"으로 나와야만 진짜로 없다고 판단한다(FR-033 개정). (2) 참조 창을 화면 밖에 두되 어느 정도 크기가 있는 보통 창으로 바꿔 조회 신뢰성을 높였다.
- Q: (사용자 직접 지적, 위 이중 확인 수정 이후에도 재발) 데스크톱 1번에서 범위 2~3을 줬는데 1→2→19→20처럼 여전히 널뛴다. → A: 근본 원인을 다시 진단해 찾아냈다 — Windows 표준 "새 데스크톱 추가" 단축키(Win+Ctrl+D)는 지금 어느 데스크톱에 있든 상관없이 항상 전체 가상 데스크톱 목록의 **맨 끝**에 새 데스크톱을 추가한다("바로 다음 자리"에 끼워 넣지 않는다). 이 때문에 이동 여부 오판 한 번(고정된 두 번의 짧은 확인으로도 여전히 발생할 수 있었다)이 곧바로 큰 점프로 이어졌다 — 예컨대 이미 18개의 데스크톱이 있는 상태에서 오판하면 새 데스크톱은 19번에 만들어진다. 이를 근본적으로 고치기 위해 고정된 두 번 확인 방식을 버리고, 전환 키 입력 후 이동이 실제로 감지될 때까지(또는 넉넉한 제한 시간이 다 될 때까지) 짧은 간격으로 계속 재확인하는 방식으로 바꿨다(FR-033 재개정) — 제한 시간 내내 단 한 번도 이동이 감지되지 않아야만 "그 데스크톱이 없다"고 최종 판단한다. 실제로 데스크톱 18개를 만들어 둔 뒤 데스크톱 1번에서 범위 2~3을 다시 시도해, 정확히 2·3번만 생성되고 19·20번으로 튀지 않음을 확인했다.
- Q: (사용자 직접 지적, 위 폴링 방식 수정 이후에도 재발) 계속 같은 문제가 발생하며, 이동 감지에 실제로 어떤 공식 API 정보를 쓰는지 전부 알려달라. → A: 공식 API(`IVirtualDesktopManager`)는 `IsWindowOnCurrentVirtualDesktop`(창이 지금 활성 데스크톱에 있는지 bool)·`GetWindowDesktopId`(창이 고정된 데스크톱의 GUID)·`MoveWindowToDesktop`(창을 특정 GUID 데스크톱으로 이동) 세 개뿐이며, "지금 몇 번째 데스크톱인지"·"총 몇 개인지"를 직접 알려주는 공식 API는 없다는 점을 다시 확인했다. 진단 로그를 붙여 정밀 조사한 결과, FR-033/FR-034의 이동 판정에 써 온 **1회용 참조 창(만들고 곧바로 조회한 뒤 버리는 방식)** 자체가 이 환경에서 근본적으로 신뢰할 수 없다는 것이 드러났다 — 어떤 실행에서는 실제 이동이 있어도 계속 "이동 안 함"으로, 다른 실행에서는 반대로 실제로는 멈춰 있는데 계속 "이동함"으로 나오는 등 일관성이 없었다(창 크기·화면 안/밖 위치·작업표시줄 노출 여부·기다리는 시간을 모두 바꿔봐도 마찬가지). 반면 세션 내내 살아있는 **데스크톱별 플로팅 창(FloatingWindowForm)을 기준으로 한 조회는 모든 테스트에서 한 번도 어긋난 적이 없었다.** 그래서 이동 판정 방식 자체를 근본적으로 바꿨다 — (1) 실제 데스크톱 1번을 찾는 과정(FR-034)은 판정에 의존하지 않고, `Ctrl+Win+Left`가 이미 첫 번째 데스크톱에서는 항상 안전한 no-op이라는 Windows 표준 동작을 이용해 충분히 넉넉한 횟수만큼 무조건 왼쪽으로 이동시키는 방식으로 바꿨다(판정 자체가 필요 없어짐). (2) 범위 시작까지의 이동과 범위 안 순회(FR-020, FR-022)는 1회용 참조 창 대신, 이미 신뢰성이 검증된 플로팅 창 자체를 이동 판정 기준으로 재사용하도록 바꿨다 — 범위 시작보다 앞선(순회 대상이 아닌) 데스크톱에서는 지나가는 동안만 임시로 플로팅 창을 만들었다가 범위 시작에 도달하면 정리한다. 데스크톱 18개를 실제로 만들어 둔 뒤 데스크톱 4번에서 범위 2~3(뒤로 여러 번 이동해야 하는 경우 포함)으로 재현해, 정확히 2·3번만 생성되고 더 이상 엉뚱하게 점프하지 않음을 확인했다.

- Q: (사용자 직접 요청, 실사용 피드백 6건) ① 목표에 도달("완료")한 뒤에도 원형 진행률 그래픽이 마지막 채움 상태로 남아 있는 게 이상하다 — 완료되면 사라지게 해달라. ② 플로팅 창 상세 보기의 일시정지 버튼 "일시정지" 텍스트가 잘려 보인다. ③ 상세 보기의 커스텀 닫기 버튼 "×" 텍스트가 살짝 잘려 보인다. ④ 시작 입력 폼의 "진행률 원 표시 (...)" 체크박스 텍스트 끝부분이 잘려서 안 보인다. ⑤ 시작하기 전에 몇 초간 화면이 멈추는데(순회 시작 데스크톱을 찾는 과정), 정확한 대기 시간을 알 수 있다면 시작 입력 폼의 "시작" 버튼 근처에 표시해달라. ⑥ 시작 입력 폼을 아예 '입력부'와 '확인부'로 나누고(거창하지 않게 얇은 수평 구분선 하나로만 구분), 확인부에는 총 예상 실행 시간·⑤의 안내 문구·"시작" 버튼을, 입력부에는 나머지 입력 필드를 두자. → A: 모두 반영한다. (①) FR-036에 "목표 총 전환 횟수에 도달하면(FR-015) 원형 그래픽을 숨긴다"는 조건을 추가한다 — 더 이상 "다음 전환까지 남은 시간"이라는 개념 자체가 없으므로 마지막 채움 상태로 얼어붙어 있는 것은 오해를 준다. (②③④) 근본 원인을 진단한 결과, `AutoScaleMode.None`으로 고정 픽셀 좌표를 쓰는 이 폼들의 버튼·체크박스 크기가 실측(이 세션 환경의 100% 배율) 기준으로 여유 있게 잡혀 있었음에도, 사용자의 실제 화면(더 높은 DPI 배율)에서는 같은 글자가 더 크게 렌더링되어 고정 픽셀 크기를 넘어설 수 있다는 것을 확인했다 — 즉 한 환경에서 측정한 고정 크기는 다른 DPI 배율에서는 근본적으로 신뢰할 수 없다. 이를 해결하기 위해 상세 보기의 일시정지·닫기(×) 버튼과 시작 입력 폼의 체크박스 3개를 모두 `AutoSize`(버튼은 `AutoSizeMode.GrowAndShrink`)로 바꿔, 어떤 DPI 환경에서 실행되든 그 자리에서 실제로 계산된 글꼴 크기에 맞춰 스스로 크기를 정하도록 했다 — 특정 환경에서 측정한 고정 픽셀 값에 더 이상 의존하지 않는다. (⑤) 시작 전 대기 시간 중 "실제 데스크톱 1번을 찾는" 단계(FR-034)는 뒤로 이동 시도 횟수 × 시도 간 지연으로 정해지는 고정값이라 상황과 무관하게 정확히 계산할 수 있음을 확인했다(현재 구현 기준 18초) — 이 값을 새 FR-039로 명시해 시작 입력 폼에 표시한다. 다만 그 이후 범위 안 데스크톱을 방문·생성하며 준비하는 시간(FR-033)은 이미 존재하는 데스크톱 수에 따라 달라져 정확한 초로 예측할 수 없으므로, 이 부분은 정성적으로만("조금 더 걸릴 수 있음") 안내한다. 2026-08-12 세션 ⑤에서 보류했던 것은 시작 단계 전용의 실시간 "진행률 표시" UI(진행 상황을 동적으로 갱신하는 컴포넌트)였고, 이번 요청은 제출 전 시작 폼에 고정된 안내 문구 한 줄을 두는 것뿐이라 훨씬 가볍다 — 오버엔지니어링 우려 없이 반영 가능하다고 판단했다. (⑥) 새 FR-038을 신설해 시작 입력 폼을 입력부/확인부로 나누고, 확인부(총 예상 실행 시간, ⑤의 대기 안내, 시작 버튼)와 입력부(나머지 입력 필드)를 얇은 수평 구분선 하나로 구분하도록 명시한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 정해진 간격 자동 강제 전환 (Priority: P1)

여러 가상 데스크톱을 서로 다른 작업 맥락으로 나눠 쓰는 사용자가 앱을 실행할 때 전환 간격, 순회할 데스크톱 범위(시작 번호~끝 번호), 총 전환 횟수를 입력하면, 앱은 그 간격마다 목표 횟수에 도달할 때까지 지정한 범위 안에서 자동으로 다음 가상 데스크톱으로 전환해준다. 사용자는 전환 시점을 스스로 기억하거나 직접 조작할 필요가 없다.

**Why this priority**: decision.md에서 확인된 이 기능의 핵심 동기(포모도로식 집중력 강제 전환)를 직접 충족하는 부분이며, 이것 없이는 나머지 기능(남은 시간/횟수 표시)이 의미가 없다.

**Independent Test**: 앱을 실행하고 아무 조작도 하지 않은 채로 설정된 간격이 지나가는 것을 관찰 — 가상 데스크톱이 자동으로 전환되면 성공.

**Acceptance Scenarios**:

1. **Given** 앱이 실행 중이고 현재 데스크톱 1번에 있음, **When** 설정된 간격이 경과함, **Then** 데스크톱 2번으로 자동 전환된다.
2. **Given** 앱이 마지막 데스크톱에 있음, **When** 설정된 간격이 경과함, **Then** 첫 번째 데스크톱으로 되돌아가 순환한다.
3. **Given** 사용자가 플로팅 창을 닫아 종료를 확정함, **When** 이 동작이 수행됨, **Then** 더 이상 자동 전환이 일어나지 않는다.
4. **Given** 누적 전환 횟수가 사용자가 입력한 총 전환 횟수에 도달함, **When** 다음 간격이 되어도, **Then** 더 이상 자동 전환이 일어나지 않고, 플로팅 창은 열린 채로 최종 통계를 계속 보여준다.
5. **Given** 사용자가 방금 앱을 실행함, **When** 앱이 시작 입력을 받아 초기 설정을 진행함, **Then** 사용자의 추가 조작 없이 각 데스크톱에 플로팅 창이 자동으로 하나씩 생성·배치되고, 원래 있던 데스크톱으로 돌아온 뒤 평소 회전이 시작된다.
6. **Given** 사용자가 데스크톱 범위 3~7을 입력함, **When** 앱이 초기 설정을 시작함, **Then** 앱은 먼저 범위의 시작인 3번 데스크톱까지 이동한 뒤, 3·4·5·6·7번 데스크톱에만 플로팅 창을 생성·배치한다 (1·2번 데스크톱은 대상에서 제외).
7. **Given** 데스크톱 범위 3~7로 회전 중이고 현재 7번 데스크톱에 있음, **When** 설정된 간격이 경과함, **Then** 범위의 시작인 3번 데스크톱으로 되돌아가 순환한다(1번으로 가지 않음).
8. **Given** 사용자가 목표 사이클 수를 3, 데스크톱 범위를 1~3으로 입력함, **When** 앱이 초기 설정 후 회전을 시작함, **Then** 시스템은 내부적으로 목표 총 전환 횟수를 9(3사이클 × 3데스크톱)로 환산해 회전을 진행하며, 9번째 전환 이후에는 더 이상 자동 전환하지 않는다.
9. **Given** 사용자가 데스크톱 범위 3~5를 입력했지만 실행 시점에 실제로는 가상 데스크톱이 1개(현재 위치)뿐임, **When** 앱이 초기 탐색·초기 설정을 진행함, **Then** 존재하지 않는 데스크톱으로의 전환 시도마다 새 가상 데스크톱을 자동으로 생성해 그 자리를 채우고, 최종적으로 3·4·5번에 해당하는 서로 다른 실제 데스크톱 각각에 플로팅 창이 하나씩 배치된다.
10. **Given** 가상 데스크톱이 이미 4개 떠 있고 사용자가 그중 2번째 데스크톱에서 앱을 실행해 범위 3~5를 입력함, **When** 앱이 초기 탐색을 진행함, **Then** 시스템은 먼저 실제 데스크톱 1번을 스스로 찾아낸 뒤 그 기준으로 이동해, 이미 존재하는 3·4번 데스크톱은 재사용하고 아직 없는 5번 데스크톱만 새로 생성한다 — 6번 이후의 불필요한 데스크톱은 생성하지 않는다.

### User Story 2 - 실수로 인한 종료 방지와 신뢰할 수 있는 전환 검증 (Priority: P1)

사용자는 플로팅 창을 실수로 닫아 프로그램이 갑자기 멈추는 일을 원하지 않는다. 창을 닫으려 하면 확인을 한 번 거치게 하고, 정말 끄기로 확정했을 때만 프로그램이 종료되기를 원한다. 또한 프로그램이 실제로 의도한 데스크톱으로 전환됐는지 스스로 확인하고, 실패하면 재시도해주기를 원한다.

**Why this priority**: 사용자가 명시적으로 지적한 핵심 우려("제대로 작동하지 않으면 거슬리기만 하는 프로그램이 된다")를 직접 해결하는 부분이며, 이것 없이는 User Story 1이 보여주는 "자동 전환"의 신뢰성 자체가 흔들린다.

**Independent Test**: 플로팅 창을 닫아보고 확인 창이 뜨는지, 취소하면 계속 동작하는지 확인. 전환 실패를 유발해보고(테스트 환경에서) 재시도가 일어나는지 확인.

**Acceptance Scenarios**:

1. **Given** 플로팅 창이 열려 있음, **When** 사용자가 닫기를 시도함, **Then** "정말 종료할까요?" 확인 창이 뜬다.
2. **Given** 확인 창이 떠 있음, **When** 사용자가 취소를 선택함, **Then** 플로팅 창은 닫히지 않고 전환·검증·카운트는 계속 정상 동작한다.
3. **Given** 확인 창이 떠 있음, **When** 사용자가 종료를 확정함, **Then** 프로그램 전체(모든 데스크톱의 창, 전환, 검증 포함)가 종료된다.
4. **Given** 전환을 시도함, **When** 검증 결과 의도한 데스크톱에 도달하지 못했음이 확인됨, **Then** 시스템은 키 입력을 재시도한다.
5. **Given** 재시도 한도까지 시도해도 의도한 데스크톱에 도달하지 못함, **When** 재시도가 모두 소진됨, **Then** 시스템은 실제로 확인된 데스크톱을 새 기준으로 삼아 내부 상태(현재 위치, 전환 횟수)를 보정한다.

### User Story 3 - 남은 시간 확인과 최소/상세 보기 전환 (Priority: P1)

사용자는 작업 중 언제든 화면 위에 항상 떠 있는 작은 플로팅 창을 통해 다음 자동 전환까지 남은 시간을 즉시 확인할 수 있다. 평소에는 화면을 가리지 않도록 테두리 없이 남은 시간 숫자만 표시되고, 더 자세한 정보(총 예상 실행 시간, 종료까지 남은 시간, 데스크톱별 전환 횟수)가 필요하면 창을 클릭해 상세 보기로 전환할 수 있다.

**Why this priority**: decision.md의 문제 정의("남은 시간에 대한 가시성 부재")를 직접 해결하며, User Story 1의 자동 전환과 짝을 이루는 최소 기능이다. 최소/상세 보기 전환은 사용자가 명시적으로 요청한 UX로, 평소에는 화면을 방해하지 않으면서 필요할 때만 자세한 정보를 볼 수 있게 해준다.

**Independent Test**: 앱 실행 후 다른 창으로 작업하면서 플로팅 창만 보고 남은 시간 숫자가 줄어드는 것을 확인 — 실제 전환 시점과 표시된 "0"이 일치하면 성공. 창을 클릭해 상세 보기로 전환되는지, 다시 클릭해 최소 보기로 돌아오는지 확인.

**Acceptance Scenarios**:

1. **Given** 앱이 실행 중, **When** 사용자가 다른 창(전체화면 포함 여부는 Assumptions 참고)을 사용 중, **Then** 플로팅 창에 남은 시간 숫자가 계속 보인다.
2. **Given** 자동 전환이 방금 일어남, **When** 새 간격이 시작됨, **Then** 남은 시간 표시가 설정된 전체 간격 값으로 리셋된다.
3. **Given** 플로팅 창이 최소 보기 상태임, **When** 사용자가 창을 클릭함, **Then** 총 예상 실행 시간·종료까지 남은 시간·데스크톱별 전환 횟수를 보여주는 상세 보기로 바뀐다.
4. **Given** 플로팅 창이 상세 보기 상태임, **When** 사용자가 창을 다시 클릭함, **Then** 남은 시간 숫자만 보이는 최소 보기로 되돌아간다.
5. **Given** 플로팅 창이 처음 생성됨, **When** 초기 배치가 이루어짐, **Then** 화면 상단 중앙(12시 방향)에 테두리 없는 상태로 나타난다.
6. **Given** 플로팅 창이 화면 상단 중앙에 있음, **When** 사용자가 창 본문을 마우스로 눌러 드래그함, **Then** 원하는 위치로 자유롭게 옮길 수 있다 (테두리가 없어 제목 표시줄 대신 창 본문으로 드래그한다).
7. **Given** 플로팅 창이 상세 보기 상태임, **When** 사용자가 상세 보기의 커스텀 닫기(×) 버튼을 클릭함, **Then** 최소 보기를 닫으려 할 때와 동일하게 "정말 종료할까요?" 확인 창이 뜬다.
8. **Given** 사용자가 시작 입력 폼에서 "사이클 번호 표시" 옵션을 켜고 시작함, **When** 회전이 진행 중임, **Then** 최소 보기의 남은 시간 앞에 현재 진행 중인 사이클 번호가 "[N번째] " 형식으로 함께 표시된다(예: "[2번째] 137초"). "초 단위 표시" 옵션을 끄면 숫자 뒤의 "초"가 빠진다.
9. **Given** 사용자가 플로팅 창을 드래그해 화면 작업 영역 테두리 가까이로 이동시킴, **When** 창이 테두리에서 설정된 임계 거리 이내로 들어옴, **Then** 창이 그 테두리에 자동으로 달라붙어 배치되며, 다시 임계 거리를 벗어나게 드래그하면 자석 효과 없이 자유롭게 이동한다.
10. **Given** 플로팅 창이 상세 보기 상태임, **When** 사용자가 일시정지 버튼을 클릭함, **Then** 남은 시간 카운트다운과 자동 전환 시도가 모두 멈추고, 버튼 표시가 "재개"로 바뀐다.
11. **Given** 일시정지 상태임, **When** 사용자가 (같은 창이든 다른 데스크톱의 창이든) 재개 버튼을 클릭함, **Then** 멈췄던 남은 시간부터 카운트다운과 자동 전환이 다시 시작된다.

### User Story 4 - 데스크톱별 전환 횟수 확인 (Priority: P2)

사용자는 플로팅 창에서 이번 실행 세션 동안 각 가상 데스크톱으로 몇 번 전환했는지 누적 횟수를 확인할 수 있다.

**Why this priority**: decision.md의 문제 정의("전환 이력에 대한 가시성 부재")를 해결하지만, 앞선 스토리들이 먼저 동작해야 의미가 있는 부가 정보이므로 P2로 둔다.

**Independent Test**: 앱을 실행한 채 여러 번의 자동 전환이 일어나도록 기다린 뒤, 플로팅 창의 데스크톱별 횟수가 실제 자동 전환 횟수와 일치하는지 확인.

**Acceptance Scenarios**:

1. **Given** 앱이 막 시작됨, **When** 아직 전환이 한 번도 없었음, **Then** 모든 데스크톱의 전환 횟수가 0으로 표시된다.
2. **Given** 데스크톱 2번으로 자동 전환이 일어남, **When** 플로팅 창을 확인함, **Then** 데스크톱 2번의 횟수가 1 증가해 표시된다.

---

### Edge Cases

- 사용자가 앱 실행 중 `Ctrl+Win+←/→` 등으로 직접 데스크톱을 전환하면 어떻게 되는가? → 다음 검증 시점(자동 전환 시도 직후)에 해당 데스크톱 창 조회로 실제 위치가 예상과 다름이 확인되며, 재시도 또는 상태 보정이 적용된다. 다만 두 검증 시점 사이(간격 도중)에 실시간으로 감지하지는 않는다.
- 사용자가 입력한 데스크톱 범위가 실제 존재하는 가상 데스크톱 수와 다르면(예: 범위 끝이 실제보다 큼) 어떻게 되는가? → 앱은 사용자가 입력한 범위를 그대로 신뢰하며, 실제 개수와의 불일치를 검증하지 않는다(범위 밖, Assumptions 참고). 존재하지 않는 데스크톱으로의 이동 시도는 다른 검증/재시도/보정 경로(FR-017~019)와 동일하게 처리된다.
- 범위의 끝이 시작보다 작으면(예: 7~3) 어떻게 되는가? → 유효하지 않은 입력으로 간주해 앱은 시작을 거부하고 다시 입력하도록 요구한다.
- 범위가 데스크톱 1개짜리(시작=끝, 예: 5~5)면 어떻게 되는가? → 순환 전환은 항상 같은 데스크톱으로 "전환"을 시도하는 동작이 되며, 이는 정상 동작으로 간주한다(에러 아님).
- 시뮬레이션한 키 입력이 다른 프로그램(단축키를 가로채는 유틸리티 등)에 의해 무시되면 어떻게 되는가? → 전환 시도 직후 검증되며, 의도한 데스크톱에 도달하지 못했으면 재시도한다(FR-017~FR-019). 재시도 한도 내에 해결되지 않으면 실제 위치를 기준으로 상태를 보정한다.
- 플로팅 창을 닫으려 하면 어떻게 되는가? → "정말 종료할까요?" 확인 창이 뜬다. 취소하면 아무 일도 일어나지 않고 계속 동작한다. 종료를 확정하면 프로그램 전체(다른 데스크톱의 창 포함)가 함께 종료된다.
- 확인 창이 떠 있는 동안에도 전환 타이머는 계속 진행되는가? → 그렇다. 확인 창은 그 창 하나의 닫기 여부만 묻는 것이며, 사용자가 응답하기 전까지 전환·검증·카운트는 평소대로 계속된다(Assumptions 참고).
- 목표 전환 횟수에 도달한 뒤에도 앱을 끄지 않고 계속 두면 어떻게 되는가? → 전환은 멈춘 채 플로팅 창은 열린 상태를 유지하며 최종 통계(총 전환 횟수, 데스크톱별 전환 횟수)만 계속 표시한다. 사용자가 창을 닫고 종료를 확정할 때까지 대기한다.
- 총 전환 횟수를 0 이하로 입력하면 어떻게 되는가? → 유효하지 않은 입력으로 간주해 앱은 시작을 거부하고 1 이상의 값을 다시 입력하도록 요구한다 (Assumptions 참고).
- 마지막 데스크톱에서 처음으로 되돌아가기 위해 연속으로 보낸 여러 키 입력 중 일부가 씹혀 누락되면 어떻게 되는가? → 입력 사이 지연(FR-016)으로 발생 확률을 낮추고, 발생하더라도 전환 직후 검증(FR-017)이 이를 감지해 재시도하거나 상태를 보정한다.
- 재시도 한도까지 다 써도 의도한 데스크톱에 도달하지 못하면 무한정 재시도하는가? → 아니다. 재시도 횟수에는 상한이 있으며, 상한 도달 후에는 실제로 확인된 위치를 새 기준으로 삼아 내부 상태를 보정하고 다음 간격으로 넘어간다(FR-019).
- 데스크톱마다 창이 하나씩 뜨는데, Alt+Tab이나 작업표시줄에서 여러 개로 보이지 않는가? → 일반 창이므로 숨기지 않는다. Windows의 "작업표시줄에 표시할 창" 설정(현재 데스크톱만 / 모든 데스크톱)에 따라 사용자에게는 항상 최대 1개(현재 데스크톱 것)만 보이거나, 데스크톱 개수만큼 보일 수 있다 — 이는 OS 설정에 따른 정상적인 차이로 간주하고 앱이 별도로 감추지 않는다.
- 시작 시 데스크톱마다 창을 배치하는 과정은 사용자가 직접 해야 하는가? → 아니다. 앱이 시작할 때 자동으로 각 데스크톱을 한 번씩 순회하며 창을 생성·배치한다(FR-020). 사용자는 수동으로 창을 옮길 필요가 없으며, 이 과정 중 화면이 짧게 여러 데스크톱을 오가는 것이 보일 수 있다(정상 동작).
- 범위의 시작이 1이 아니면(예: 3~7) 앱은 어떻게 그 데스크톱까지 이동하는가? → 앱 실행 시점의 데스크톱을 기준으로, 범위 시작 번호까지 필요한 만큼 자동으로 이동한 뒤(초기 탐색) 기존 초기 설정 과정을 시작한다. 이동 도중에도 화면이 짧게 여러 데스크톱을 오가는 것이 보일 수 있다(정상 동작).
- 플로팅 창을 드래그로 옮기는 중에 클릭으로 오인되어 최소/상세 보기가 실수로 바뀌지 않는가? → 마우스를 누른 채 일정 거리 이상 움직이면 드래그로 간주하고, 움직임 없이 누르고 뗀 경우만 클릭(보기 전환)으로 처리한다.
- 검증·재시도(FR-017~019)가 여러 차례 걸리는 동안 플로팅 창의 화면이 멈춰 보이지는 않는가? → 아니다. 검증/재시도 시퀀스가 진행 중이어도 매초 화면 갱신은 계속되어야 한다(FR-028) — 갱신 자체를 멈추고 기다리는 방식은 특정 데스크톱의 창이 남은 시간 "0"에 멈춰 보이는 결함으로 이어졌던 적이 있다.
- 세션 도중 사용자가 가상 데스크톱의 순서를 바꾸거나 데스크톱을 추가/삭제하면 어떻게 되는가? → 시작 시 입력한 개수 불일치와 마찬가지로 범위 밖이다. 검증/재시도/보정(FR-017~019)이 안전망으로 작동해 아예 방치되지는 않지만, 원래 의도했던 순서를 정교하게 복구하는 것은 보장하지 않는다. 필요하면 앱을 재시작해 처음부터 다시 설정해야 한다.
- 사용자가 입력한 범위의 데스크톱이 실행 시점에 실제로 존재하지 않으면(예: 현재 가상 데스크톱이 1개뿐인데 범위 3~5를 입력) 어떻게 되는가? → 실제 데스크톱 1번부터 범위 안의 각 데스크톱을 순서대로 방문하며(FR-020, FR-022), 다음 데스크톱으로 넘어갈 때마다 그 데스크톱을 대표하는(이미 신뢰성이 검증된) 플로팅 창을 기준으로 실제 이동이 일어났는지 공식 API로 확인한다. 이동이 없었으면(=그 데스크톱이 아직 없으면) Windows 표준 "새 데스크톱 추가" 단축키로 새 가상 데스크톱을 만들어 그 자리로 전환한다(FR-033). 이 과정에서 화면에 새 데스크톱이 여러 개 순간적으로 생성되는 것이 보일 수 있다(정상 동작). 이 확인 없이 맹목적으로 전환 키만 보내면, 서로 다른 범위 번호의 플로팅 창들이 모두 같은 실제 데스크톱 위에 만들어져 전환 검증이 항상 "일치"로 오판하는 결함으로 이어진다 — FR-033은 이를 방지하기 위한 요구사항이다.
- 실행 시점의 데스크톱이 맨 처음(1번)이 아니라 이미 다른 데스크톱들 사이에 있으면 어떻게 되는가(예: 데스크톱이 4개 떠 있고 2번째에서 실행)? → 시스템은 초기 탐색을 시작하기 전에, 실제 데스크톱 1번에 도달할 때까지 뒤로 이동하는 동작을 충분히 넉넉한 횟수만큼 무조건 반복한다(FR-034) — 이미 1번에 도달한 뒤에 더 시도해도 Windows 표준 동작상 아무 효과 없는 안전한 시도이므로, "몇 번째인지 판정"에 의존하지 않고도 확실하게 1번에 도달할 수 있다. 그 지점을 기준으로 범위 시작까지 이동해야 이미 존재하는 데스크톱을 최대한 재사용하고 부족한 만큼만 새로 생성한다 — 실행 시점을 무조건 1번으로 잘못 가정하면 계산이 틀어져 불필요한 데스크톱을 대량으로 만들어버리는 심각한 결함으로 이어진다(실사용 중 발견됨). 이 과정에서도 화면이 짧게 여러 데스크톱을 오가는 것이 보일 수 있다(정상 동작).
- 목표 사이클 수를 0 이하로 입력하면 어떻게 되는가? → 유효하지 않은 입력으로 간주해 앱은 시작을 거부하고 1 이상의 값을 다시 입력하도록 요구한다(FR-013, 기존 목표 총 전환 횟수와 동일한 원칙).
- 데스크톱 범위가 1개짜리(시작=끝)일 때 1 사이클은 몇 번의 전환인가? → 1번이다 — 그 데스크톱 하나를 순회하는 것이 1사이클이며, 같은 데스크톱으로의 "전환" 시도도 정상 동작으로 간주한다(기존 FR-002 Edge Case와 동일한 원칙).
- 상세 보기의 커스텀 닫기 버튼을 눌러도 최소 보기에서 닫기를 시도할 때와 동작이 다른가? → 아니다. 둘 다 동일하게 FR-008의 "정말 종료할까요?" 확인 절차로 이어진다.
- 창을 화면 테두리 쪽으로 드래그하다가 임계 거리를 다시 벗어나면 자석 효과가 풀리는가? → 그렇다. 스냅은 드래그 중 실시간으로 창이 테두리에서 임계 거리 이내에 있을 때만 적용되며, 벗어나면 일반 자유 이동으로 돌아간다.
- 일시정지 중에 목표 총 전환 횟수에 이미 도달해 있으면 일시정지 버튼은 어떻게 되는가? → 목표 도달 후에는 일시정지 개념이 의미가 없으므로 버튼을 비활성화한다.
- 일시정지 중에 검증/재시도(FR-017~019) 시퀀스가 이미 진행되고 있었다면 어떻게 되는가? → 이미 시작된 시퀀스는 끝까지 마치며, 그 이후의 새로운 자동 전환 시도만 멈춘다. 일시정지 중에도 플로팅 창 화면 갱신(FR-028)은 계속된다.
- 데스크톱마다 창이 따로 있는데, 한 창에서 일시정지를 누르면 다른 데스크톱의 창에는 어떻게 반영되는가? → 일시정지 상태는 로테이션 세션 하나에 속한 값이므로, 어느 창에서 누르든 모든 창에 즉시 동일하게 반영된다(FR-006의 데스크톱별 전환 횟수와 같은 원리).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 실행 중 정해진 간격마다, 사용자가 입력한 총 전환 횟수에 도달할 때까지 자동으로 다음 가상 데스크톱으로 전환을 시도해야 한다 (사용자의 추가 조작 없이).
- **FR-002**: 시스템은 지정된 범위의 마지막 데스크톱에서 전환할 때 범위의 첫 데스크톱으로 되돌아가 순환해야 한다 (범위 안의 데스크톱을 순서대로 순환하며, 누적 전환 횟수가 총 전환 횟수에 도달할 때까지 반복될 수 있다). 범위 안의 각 데스크톱은 동일한 빈도로 방문되어야 하며(균일 순회), 끝에서 방향을 바꾸는 방식은 사용하지 않는다.
- **FR-003**: 시스템은 사용자가 실행 시 순회할 가상 데스크톱의 범위를 시작 번호와 끝 번호(1-based, 둘 다 1 이상, 끝 ≥ 시작)로 직접 입력하도록 해야 한다 (OS로부터 실제 개수를 조회하지 않으므로). 예: 시작 3, 끝 7 입력 시 데스크톱 3·4·5·6·7이 순회 대상이다. 입력한 범위의 데스크톱이 실행 시점에 실제로 존재하지 않으면, 시스템은 이를 맹목적으로 신뢰하지 않고 FR-033에 따라 부족한 데스크톱을 자동으로 생성해 채운다.
- **FR-004**: 시스템은 데스크톱마다 하나씩, 항상 위(always-on-top)로 표시되는 테두리 없는(borderless) 플로팅 창을 제공해야 한다. 이 창들은 (제목 표시줄이 없다는 점을 제외하면) 일반 창이며 숨겨지지 않는다.
- **FR-005**: 각 플로팅 창의 상세 보기는 다음 자동 전환까지 남은 시간과, 프로그램 종료까지 남은 전체 시간을 실시간으로 표시해야 한다.
- **FR-006**: 각 플로팅 창의 상세 보기는 현재 실행 세션 동안 각 데스크톱으로 전환된 누적 횟수를 데스크톱별로 표시해야 한다.
- **FR-007**: 시스템은 전환 횟수와 남은 시간 상태를 세션(앱 실행) 범위에서만 유지하며, 앱을 재시작하면 초기화해야 한다.
- **FR-008**: 사용자가 플로팅 창을 닫으려 시도하면, 시스템은 "정말 종료할까요?" 확인을 요청해야 한다.
- **FR-009**: 사용자가 확인 창에서 종료를 확정하면, 시스템은 프로그램 전체(모든 데스크톱의 창, 전환·검증 동작 포함)를 종료해야 한다.
- **FR-010**: 사용자가 확인 창에서 취소를 선택하면, 해당 플로팅 창은 닫히지 않고 계속 열려 있어야 하며 전환·검증·카운트는 중단 없이 계속되어야 한다.
- **FR-011**: 시스템은 앱 실행 시 사용자가 전환 간격을 직접 입력/설정할 수 있어야 한다 (고정 하드코딩 값이 아니라, 매 실행마다 원하는 간격으로 조정 가능해야 한다).
- **FR-012**: 시스템은 Windows 환경에서만 동작하면 되며, 다른 운영체제 지원은 요구되지 않는다.
- **FR-013**: 시스템은 앱 실행 시 사용자가 목표 사이클 수를 직접 입력하도록 해야 한다 (1 이상의 정수만 유효한 값으로 받아들인다). 1 사이클은 지정한 범위 안의 데스크톱을 한 번씩 모두 순회하는 것을 의미하며, 시스템은 이를 목표 총 전환 횟수(목표 사이클 수 × 순회 대상 데스크톱 개수)로 환산해 FR-001·FR-014·FR-015 등 기존 로직에 사용해야 한다.
- **FR-014**: 시스템은 입력된 전환 간격과 (FR-013에 따라 환산된) 목표 총 전환 횟수를 곱해 총 예상 실행 시간을 계산하고, 앱 시작 시(시작 입력 폼)와 플로팅 창 상세 보기 상태일 때 사용자에게 보여줘야 한다 (최소 보기 상태에서는 FR-023에 따라 숨겨진다).
- **FR-015**: 시스템은 누적 전환 횟수가 목표 총 전환 횟수에 도달하면 자동 전환을 멈춰야 하며, 이때 플로팅 창을 닫지 않고 열어 둔 채로 최종 통계(총 전환 횟수, 데스크톱별 전환 횟수)를 계속 표시해야 한다.
- **FR-016**: 마지막 데스크톱에서 첫 번째 데스크톱으로 되돌아가기 위해 여러 번의 키 입력을 연속으로 보내야 하는 경우, 시스템은 각 키 입력 사이에 OS의 전환 애니메이션이 끝날 시간을 확보하기 위한 지연을 두어야 한다. 이 지연은 (한 번이든 여러 번이든) 그 전환 시도의 **마지막** 키 입력 이후, FR-017의 검증을 시작하기 전에도 동일하게 적용해야 한다 — 그렇지 않으면 애니메이션이 끝나기 전에 검증해 불일치로 오판하고, 불필요한 재시도 키 입력을 추가로 보내게 된다(실제 발생했던 결함: 범위 끝→시작으로 2번만 이동하면 되는 경우에 3번째 키 입력이 나감).
- **FR-028**: 전환 검증·재시도 시퀀스가 진행되는 동안에도, 시스템은 모든 플로팅 창의 표시(남은 시간 등)를 매초 계속 갱신해야 한다 — 검증/재시도가 여러 차례 걸리더라도 화면이 멈춘 것처럼 보여서는 안 된다.
- **FR-017**: 시스템은 자동 전환을 시도한 직후, 공식 API로 데스크톱별 플로팅 창을 조회해 실제로 의도한 데스크톱에 도달했는지 검증해야 한다.
- **FR-018**: 검증 결과 의도한 데스크톱에 도달하지 못한 경우, 시스템은 정해진 한도까지 키 입력을 재시도해 의도한 데스크톱에 도달하도록 해야 한다.
- **FR-019**: 재시도 한도 내에도 의도한 데스크톱에 도달하지 못하면, 시스템은 무한정 재시도하지 않고 검증으로 확인된 실제 데스크톱을 새 기준으로 삼아 내부 상태(현재 위치, 데스크톱별 전환 횟수 집계)를 보정해야 한다.
- **FR-020**: 시스템은 앱 시작 시 사용자의 수동 개입 없이, 지정된 범위 안의 각 가상 데스크톱을 순서대로 한 번씩 자동으로 방문하며 데스크톱별 플로팅 창을 생성·배치해야 한다. 이 초기 설정이 끝나면 원래 있던 데스크톱으로 돌아와 평소의 회전 동작을 시작해야 한다.
- **FR-021**: 시스템은 각 플로팅 창을 초기에는 화면 상단 중앙(12시 방향)에 테두리 없는 상태로 배치해야 한다. 이후 사용자는 창 본문을 드래그하여 자유롭게 원하는 위치로 옮길 수 있어야 한다 (제목 표시줄이 없으므로 창 본문이 드래그 대상이다).
- **FR-022**: 시스템은 앱 시작 시, 지정된 범위의 시작 데스크톱이 실행 시점의 현재 데스크톱과 다르면 범위 시작까지 자동으로 이동(초기 탐색)한 뒤 FR-020의 초기 설정을 수행해야 한다.
- **FR-023**: 플로팅 창의 기본 상태(최소 보기)는 다음 자동 전환까지 남은 시간(초) 숫자만 표시해야 하며, 그 외 정보(총 예상 실행 시간, 종료까지 남은 시간, 데스크톱별 전환 횟수)는 숨겨야 한다.
- **FR-024**: 사용자가 플로팅 창을 (드래그가 아닌) 클릭하면, 시스템은 최소 보기와 상세 보기(FR-005, FR-006, FR-014 내용을 모두 표시)를 서로 전환해야 한다.
- **FR-025**: 시스템은 마우스를 누른 채 일정 거리 이상 이동한 경우를 드래그로, 이동 없이 누르고 뗀 경우를 클릭으로 구분해야 한다 (드래그 도중 실수로 보기가 전환되지 않도록).
- **FR-026**: 시스템은 시작 입력 폼에 데스크톱 범위 기본값 1~3, 전환 간격 기본값 5분(300초)을 미리 채워 두어야 한다.
- **FR-027**: 시스템은 입력된 데스크톱 범위의 끝 번호가 시작 번호보다 작으면 유효하지 않은 입력으로 간주해 시작을 거부하고 재입력을 요구해야 한다.
- **FR-029**: 플로팅 창 상세 보기는 커스텀 닫기(×) 버튼을 제공해야 하며, 사용자가 이를 클릭하면 FR-008의 "정말 종료할까요?" 확인 절차로 이어져야 한다. 최소 보기에는 닫기 버튼을 표시하지 않는다(화면을 가리지 않기 위함, FR-023과 일관).
- **FR-030**: 시스템은 상세 보기에 현재 진행 중인 사이클 번호와 목표 사이클 수를 표시해야 한다(예: "2 / 3 사이클").
- **FR-031**: 시스템은 시작 입력 폼에 "초 단위 표시"와 "사이클 번호 표시" 두 개의 온/오프 옵션을 제공해야 하며(둘 다 기본값 켜짐), 두 옵션은 플로팅 창 최소 보기의 남은 시간 표시 형식에 반영되어야 한다 — 초 단위 표시가 켜져 있으면 숫자 뒤에 "초"를 붙이고(꺼져 있으면 숫자만 표시), 사이클 번호 표시가 켜져 있으면 그 앞에 "[N번째] "를 붙인다(N = 현재 진행 중인 사이클 번호). 두 옵션은 동시에 켜질 수 있다(예: "[2번째] 137초").
- **FR-032**: 사용자가 플로팅 창을 드래그해 화면 작업 영역의 테두리에 근접시키면(설정된 임계 거리 이내), 시스템은 창을 해당 테두리에 맞춰 자동으로 붙여(snap) 배치해야 한다. 임계 거리를 벗어나면 일반적인 자유 이동으로 동작한다.
- **FR-033**: 시스템은 실제 데스크톱 1번부터 범위 안의 각 데스크톱을 순서대로 방문하며(FR-020, FR-022), 다음 데스크톱으로 전환하는 키 입력을 보낸 직후 그 순간까지 방문했던, 이미 신뢰성이 검증된 플로팅 창(1회용 임시 참조 창이 아님 — 실사용 중 1회용 참조 창은 이동 판정 결과가 신뢰할 수 없다는 것이 확인됐다)을 기준으로 공식 API로 실제 전환이 일어났는지 확인해야 한다. 이 확인은 이동이 감지될 때까지 충분히 넉넉한 시간 동안 반복 조회해야 하며, 그 시간 동안 단 한 번도 이동이 감지되지 않았을 때에만 "그 순번의 가상 데스크톱이 아직 존재하지 않는다"고 판단해야 한다. 존재하지 않는다고 판단되면 시스템은 Windows 표준 "새 데스크톱 추가" 단축키를 보내 새 가상 데스크톱을 생성하고 그쪽으로 전환해야 한다 — 이 단축키는 현재 위치와 무관하게 항상 전체 가상 데스크톱 목록의 맨 끝에 추가하므로, 이동 여부 판정을 오판하면 바로 옆이 아니라 이미 존재하던 다른 데스크톱들 끝까지 엉뚱하게 새로 만들며 튀어버리는 결함으로 이어진다(실사용 중 발견: 데스크톱 1번에서 범위 2~3만 줬는데 19·20번까지 점프). 이를 통해 사용자가 입력한 범위(FR-003)의 모든 데스크톱이 실제로 서로 다른 가상 데스크톱으로 존재하도록 보장해야 하며, 이미 존재하는 데스크톱은 최대한 재사용하고 부족한 만큼만 새로 생성해야 한다(불필요하게 여러 개를 추가로 만들면 안 된다). 범위 시작보다 앞선(순회 대상이 아닌) 데스크톱에서 이 과정 중 임시로 만든 플로팅 창은 범위 시작에 도달하면 정리해야 한다.
- **FR-034**: 시스템은 초기 탐색(FR-022)을 시작하기 전에, 실행 시점의 현재 데스크톱이 전체 중 몇 번째(절대 위치)인지 공식 API로 알 수 없다는 전제 하에 실제 데스크톱 1번에 도달해야 한다 — 뒤로(Previous) 방향 전환을, 실제로 있을 법한 데스크톱 개수보다 충분히 넉넉한 횟수만큼 무조건 반복 시도해야 한다(이동 여부를 판정해 도달 시점을 스스로 감지하려 하지 않는다 — 실사용 중 이런 판정이 신뢰할 수 없는 것으로 확인됐다). `Ctrl+Win+Left`는 이미 첫 번째 데스크톱에 있을 때 눌러도 항상 안전한 no-op이라는 것이 Windows 표준 동작으로 보장되므로, 이미 도달한 뒤의 나머지 시도는 아무 부작용 없이 무시된다. 이 지점을 기준으로 삼아야만 범위 시작까지 필요한 이동 칸 수를 정확히 계산할 수 있으며, 그렇지 않고 실행 시점을 무조건 절대 1번으로 가정하면 이미 다른 데스크톱들 사이에서 실행했을 때(예: 4개 중 2번째) 계산이 틀어져 FR-033의 판단 기준 자체가 잘못되어 불필요한 데스크톱을 대량으로 생성하는 결함으로 이어진다.
- **FR-035**: 시스템은 플로팅 창 상세 보기에 일시정지/재개 버튼을 제공해야 한다. 일시정지 상태에서는 남은 시간 카운트다운(FR-005)과 새로운 자동 전환 시도(FR-001)가 모두 멈춰야 하며(이미 진행 중이던 검증·재시도 시퀀스는 끝까지 마친다), 재개하면 멈췄던 지점부터 다시 진행해야 한다. 일시정지 상태는 로테이션 세션 하나에 속하므로 어느 데스크톱의 창에서 토글하든 모든 창에 즉시 동일하게 반영되어야 하며, 목표 총 전환 횟수에 이미 도달한 뒤에는 버튼을 비활성화해야 한다.
- **FR-036**: 시스템은 표시 옵션 "진행률 원 표시"가 켜져 있을 때(기본값 켜짐), 플로팅 창 최소 보기의 남은 시간 숫자 오른쪽에 원형 진행률 그래픽을 표시해야 한다. 그래픽은 두 부분으로 구성된다 — (1) 항상 완전한 원 형태를 유지하는 고정 테두리(뼈대)와 (2) 다음 자동 전환까지 남은 시간 비율(남은 시간 ÷ 전환 간격)만큼 채워지는 내부 색상. 남은 시간이 줄어들면 채워진 색상의 비율만 줄어들어야 하며, 테두리(뼈대)의 원형 형태 자체는 어떤 경우에도 찌그러지거나 깨진 모양으로 보이면 안 된다. 이 옵션이 꺼져 있으면 그래픽 없이 숫자만 표시한다(FR-023과 일관). 목표 총 전환 횟수에 도달하면(FR-015, "완료") 더 이상 "다음 전환까지 남은 시간"이라는 개념이 없으므로, 옵션이 켜져 있어도 그래픽 자체를 숨겨야 한다(마지막 채움 상태로 남아 있지 않는다).
- **FR-037**: 플로팅 창 상세 보기의 일시정지/재개 버튼(FR-035)과 커스텀 닫기 버튼(FR-029), 그리고 시작 입력 폼의 표시 옵션 체크박스(FR-031, FR-036)는 고정 픽셀 크기가 아니라 실제 렌더링 시점의 글꼴·DPI 배율을 기준으로 스스로 크기를 계산해야 한다 — 특정 환경에서 측정한 고정 크기는 다른 DPI 배율의 화면에서는 텍스트가 잘려 보일 수 있다(실사용 중 발견).
- **FR-038**: 시작 입력 폼은 '입력부'와 '확인부' 두 구역으로 나뉘어야 하며, 두 구역은 하나의 얇은 수평 구분선으로만 구분해야 한다(별도의 테두리 상자나 제목 등 거창한 시각적 구획은 두지 않는다). 확인부에는 총 예상 실행 시간 표시(FR-014)·시작 전 대기 시간 안내(FR-039)·"시작" 버튼을 배치하고, 입력부에는 그 외 나머지 입력 필드(순회 범위, 전환 간격, 목표 사이클 수, 표시 옵션 체크박스들, 오류 메시지)를 배치해야 한다.
- **FR-039**: 시작 입력 폼은 "시작" 버튼 근처에, 시작 시 실제 데스크톱 1번을 찾기 위해 소요되는 대기 시간(FR-034)을 안내하는 문구를 표시해야 한다. 이 대기 시간은 뒤로 이동 시도 횟수 × 시도 간 지연으로 정해지는 고정값이므로 정확한 초 단위 수치로 안내해야 한다. 이후 범위 안 데스크톱을 방문·생성하며 준비하는 시간(FR-033)은 기존에 존재하는 데스크톱 수에 따라 달라져 정확히 예측할 수 없으므로, 이 부분은 정성적으로만("조금 더 걸릴 수 있음" 등) 안내하면 된다.

### Key Entities

- **로테이션 세션(Rotation Session)**: 앱이 실행되어 있는 동안의 상태 — 순회 범위(시작 데스크톱 번호, 끝 데스크톱 번호), 현재(검증으로 확인된) 데스크톱 위치, 전환 간격, 목표 사이클 수와 이로부터 환산된 목표 총 전환 횟수, 지금까지 누적된 전환 횟수, 현재 진행 중인 사이클 번호, 다음 전환까지 남은 시간, 종료까지 남은 전체 시간, 계산된 총 예상 실행 시간, 목표 도달 여부, 일시정지 여부(FR-035), 마지막 검증 결과와 재시도 횟수를 포함. 앱 종료 시 사라진다.
- **데스크톱별 전환 카운트(Per-Desktop Switch Count)**: 순회 범위 안의 각 가상 데스크톱 번호에 대해 이번 세션에서 그 데스크톱으로 전환된(검증된) 횟수. 로테이션 세션에 속하며 영속화되지 않는다.
- **데스크톱별 플로팅 창(Per-Desktop Floating Window)**: 순회 범위 안의 데스크톱마다 하나씩 존재하는 테두리 없는 창. 최소 보기(남은 시간 숫자만, 표시 옵션에 따라 "초"·사이클 번호 접두어·오른쪽 원형 진행률 그래픽 포함 가능)와 상세 보기(총 통계, 커스텀 닫기 버튼 포함) 두 가지 표시 상태를 가지며 클릭으로 전환된다. 어떤 데스크톱에 속해 있는지로 전환 결과를 검증하는 역할도 겸한다. 숨겨지지 않으며, 닫으려 하면(기본 닫기 시도든 상세 보기의 커스텀 닫기 버튼이든) 종료 확인 절차를 거친다. 드래그 중 화면 테두리에 근접하면 자석처럼 달라붙는다(FR-032).
- **표시 옵션(Display Options)**: 시작 입력 폼에서 설정하는 세 개의 온/오프 값 — "초 단위 표시"(기본 켜짐), "사이클 번호 표시"(기본 켜짐, 2026-08-12 변경), "진행률 원 표시"(기본 켜짐, 2026-08-13 신설). 세션 범위에서만 유지되며, 최소 보기의 남은 시간 표시 형식(FR-031)과 원형 진행률 그래픽(FR-036)에 반영된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 앱을 실행한 뒤 별도의 수동 조작 없이도 설정된 간격마다 가상 데스크톱이 자동으로 전환되는 것을 확인할 수 있다.
- **SC-002**: 사용자는 작업 중 언제든 플로팅 창을 보는 것만으로 1초 이내에 다음 전환까지 남은 시간을 파악할 수 있다.
- **SC-003**: 사용자는 별도의 기록이나 도구 없이 플로팅 창(상세 보기)만으로 이번 세션 동안 각 데스크톱으로 몇 번 전환됐는지 확인할 수 있다.
- **SC-009**: 사용자는 평소(최소 보기) 작업 화면을 크게 가리지 않으면서도 남은 시간을 확인할 수 있다 (질적 지표: 기본 상태에서 숫자 외의 정보가 보이지 않음).
- **SC-010**: 사용자는 데스크톱 개수 대신 범위(시작~끝)를 지정해, 원하는 일부 데스크톱만 순회 대상으로 좁힐 수 있다.
- **SC-004**: 사용자는 앱을 하루 이상 켜 둔 상태로 별도의 수동 리마인더 없이 반복적으로 사용할 수 있다 (앱이 중간에 멈추거나 응답 없음 상태가 되지 않음).
- **SC-005**: 사용자는 시작 화면에서 입력한 값(전환 간격, 총 전환 횟수)만으로 프로그램이 총 얼마 동안 작동할지 실행 전에 미리 알 수 있다.
- **SC-006**: 사용자는 목표 전환 횟수에 도달한 뒤에도 창을 닫기 전까지 최종 통계를 확인할 수 있다 (통계가 갑자기 사라지지 않음).
- **SC-007**: 사용자는 플로팅 창을 실수로 닫으려 해도 확인 절차 덕분에 의도치 않게 프로그램이 꺼지지 않는다는 것을 확인할 수 있다 (질적 지표: 닫기 시도 시 확인 창이 항상 뜨고, 취소하면 동작이 끊기지 않음).
- **SC-008**: 키 입력이 씹혀 전환이 실패하는 상황에서도, 시스템은 검증과 재시도를 통해 대부분의 경우 의도한 순서를 회복한다 (질적 지표: 재시도 한도 내 회복 여부를 관찰로 확인).
- **SC-011**: 사용자는 숫자를 자세히 읽지 않고도 최소 보기의 원형 진행률 그래픽만 보고 다음 전환까지 남은 시간의 대략적인 비율을 즉시 파악할 수 있다 (질적 지표: 원의 테두리 형태는 항상 동일하게 유지되고 내부 채움 비율만 변한다).
- **SC-012**: 사용자는 시작 화면에서 "시작"을 누르기 전에, 실제 회전이 시작되기까지 최소 얼마나 기다려야 하는지 미리 알 수 있다 (SC-005의 "총 실행 시간을 미리 안다"는 것과 짝을 이루는, "언제 실제로 시작되는지"에 대한 사전 안내).

## Assumptions

- 회전 대상 범위는 앱 실행 시 사용자가 입력한 데스크톱 시작~끝 번호(1-based, 둘 다 포함)이며, 그 번호들이 실제로 존재하는지는 앱이 초기 탐색·초기 설정 과정에서 매 단계 확인하고 부족하면 자동 생성한다(FR-033) — 다만 그 이후 세션 도중 데스크톱의 순서가 바뀌거나 개수가 추가/삭제되는 경우는 별개이며, 이 경우는 재동기화를 보장하지 않는다(검증/재시도/보정이 안전망 역할만 한다).
- 시작 입력 폼의 기본값은 데스크톱 범위 1~3, 전환 간격 5분(300초)이다(FR-026). 목표 사이클 수의 기본값은 4(사용자 직접 요청으로 3에서 변경, 2026-08-12)이며, "초 단위 표시"와 "사이클 번호 표시" 모두 기본 켜짐이다(FR-013, FR-031).
- Windows는 가상 데스크톱 개수에 공식적으로 문서화된 고정 상한을 두지 않으며(시스템 메모리에 따라 달라짐), 이 프로그램도 별도의 OS 유래 상한값을 적용하지 않는다. 다만 극단적으로 큰 입력으로 인한 대량의 데스크톱 생성을 막기 위해, 시작 입력 폼의 범위 시작/끝 입력값은 기존과 같이 1~100으로 제한하는 구현 재량의 안전장치를 유지한다.
- 초기 탐색·초기 설정 중 자동 생성되는 새 데스크톱(FR-033)은 Windows 표준 단축키(Win+Ctrl+D)로 생성하며, 별도의 이름 지정이나 정리(생성된 데스크톱을 앱 종료 시 다시 삭제하는 것 등)는 하지 않는다 — 사용자가 이미 갖고 있던 데스크톱 구성에 필요한 만큼만 추가되는 것으로 간주한다.
- 데스크톱별 플로팅 창은 앱 시작 시 자동으로 각 데스크톱을 한 번씩 순회하며 생성·배치된다(FR-020) — 사용자가 수동으로 창을 옮길 필요는 없다.
- 앱은 실제 전환 결과를 확인할 때 공식적으로 문서화된 `IVirtualDesktopManager` 조회 API(데스크톱별 플로팅 창 기반)만 사용하며, 비공식·비문서화된 내부 COM 인터페이스나 강제 포커스 트릭은 사용하지 않는다 — 조회는 포커스를 빼앗지 않는 순수 읽기 동작이라 포그라운드 잠금 문제가 없다.
- 데스크톱별 플로팅 창은 일반 창이며 숨기지 않는다. Alt+Tab·작업표시줄·Task View에 노출될 수 있으며, 이는 Windows의 "작업표시줄에 표시할 창" 설정에 따라 사용자마다 다르게 보일 수 있다(범위 밖, OS 설정에 맡김).
- "정말 종료할까요?" 확인 창이 떠 있는 동안에도 전환 타이머·검증·카운트는 계속 동작한다 — 확인 창은 그 시점의 닫기 요청 하나만 다루며 나머지 동작을 멈추지 않는다.
- 재시도 한도(몇 번까지 재시도할지)의 정확한 수치는 이 스펙에서 정하지 않고 계획/구현 단계 재량으로 둔다 — 다만 반드시 유한한 상한이 있어야 하며 무한 재시도는 허용하지 않는다(FR-019).
- 플로팅 창은 항상 위(always-on-top)로 표시되며 테두리가 없다. 초기 위치는 화면 상단 중앙(12시 방향)이고 이후 창 본문 드래그로 옮길 수 있다(FR-021) — 정확한 투명도/클릭 통과 여부는 이번 스펙에서 세부 결정하지 않고 구현 재량으로 둔다.
- 사용자가 드래그로 옮긴 창 위치는 세션 범위에서만 유지된다고 가정한다 — 앱을 재시작하면 다시 초기 위치(화면 상단 중앙)로 배치된다(FR-007의 "재시작 시 초기화" 원칙과 일관).
- 클릭과 드래그를 구분하는 정확한 이동 거리 임계값은 이 스펙에서 수치화하지 않고 구현 재량으로 둔다(FR-025) — 일반적인 OS 드래그 임계값 수준이면 충분하다.
- 플로팅 창은 항상 최소 보기로 시작하며, 상세 보기 여부는 세션 범위에서만 유지된다(재시작하면 다시 최소 보기).
- 일시정지/재개는 FR-035로 포함됐다(2026-08-12). 다만 간격 실시간 조정, 시스템 트레이 상주, Windows 자동 시작 기능은 이번 버전에도 포함하지 않는다 — 창 독립적 동작 보장은 트레이 상주 대신 종료 확인 절차로 대체되었다(이번 clarify 세션에서 최종 결정).
- 원형 진행률 그래픽(FR-036, 2026-08-13 신설)의 정확한 크기·색상·부드러운 채움 전환(애니메이션) 여부는 이 스펙에서 수치화하지 않고 구현 재량으로 둔다 — 다만 테두리(뼈대)의 원형 형태가 항상 동일하게 유지되고 내부 채움 비율만 변한다는 핵심 요구(FR-036)는 반드시 지켜야 한다. 일시정지 중(FR-035)에는 채움 비율도 카운트다운과 함께 멈춰야 하며, 목표 도달 후("완료")에는 그래픽 자체를 숨긴다.
- 버튼·체크박스의 정확한 크기 계산 방식(FR-037)은 이 스펙에서 특정 API나 여백 수치를 지정하지 않고 구현 재량으로 둔다 — 다만 어떤 화면 DPI 배율에서도 텍스트가 잘리지 않아야 한다는 결과 요구만 명시한다.
- 시작 전 대기 시간 안내(FR-039)에서 정확한 초 단위로 표시하는 범위는 "실제 데스크톱 1번을 찾는" 고정 소요 시간(FR-034)까지다 — 그 이후 범위 안 데스크톱을 준비하는 시간(FR-033)은 기존 데스크톱 구성에 따라 달라지므로 의도적으로 정확한 초를 제시하지 않는다(부정확한 숫자를 제시하는 것보다 정성적 안내가 낫다고 판단). 2026-08-12 세션에서 보류했던 "시작 단계 실시간 진행률 표시 UI"와는 다른, 제출 전 고정 안내 문구 한 줄이라는 점에서 그 보류 결정과 충돌하지 않는다.
- 전환 횟수와 세션 상태는 앱 재시작 시 초기화되며, 별도 저장소에 영속화하지 않는다.
- 총 전환 횟수는 앱 실행 시 사용자가 매번 직접 입력하는 필수 값(1 이상의 정수)이며, "무제한" 옵션은 이번 버전에서 제공하지 않는다.
- "총 예상 실행 시간"은 전환 간격 × 총 전환 횟수로 계산되는 단순 안내용 값이며, 실제 시스템 타이머 오차 등으로 인한 약간의 편차는 허용 범위로 간주한다.
- 이 프로그램의 목적은 여러 작업 맥락을 적절히 오가며 순환시키는 것이지, 초 단위로 정확히 맞아떨어지는 정밀한 전환 타이밍이 아니다. 검증/재시도(FR-017~019)나 애니메이션 대기(FR-016)로 인해 실제 전환이 몇 초 늦어지는 정도는 정상 범위이며, 정확한 지연 수치를 맞추려고 애쓰기보다 "화면이 멈추지 않고 결국 안정적으로 도는 것"을 우선한다.
- 각 데스크톱을 균일한 빈도로 반복 방문하는 것이 목적이므로, 끝에서 방향을 바꾸는 핑퐁 방식은 채택하지 않고 순환(wrap) 방식을 유지한다. 이로 인해 마지막→처음 전환 시점에는 여러 번의 키 입력이 연속으로 필요하며, 입력 사이 지연과 전환 후 검증·재시도를 함께 적용해 위험을 완화한다.
