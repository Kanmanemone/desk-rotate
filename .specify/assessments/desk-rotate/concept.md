# 컨셉: Windows 가상 데스크톱 자동 전환 + 상태 표시

- **Slug**: desk-rotate
- **Created**: 2026-08-11
- **Recommended option**: Option A — 키 입력 시뮬레이션 기반 최소 로테이터

## 옵션

### Option A — 키 입력 시뮬레이션 기반 최소 로테이터
- **Sketch**: `Ctrl+Win+←/→` 키 입력을 시뮬레이션해 정해진 간격마다 자동으로 다음 데스크톱으로 넘어간다. 사용자는 실행 시 총 데스크톱 개수만 알려주고, 앱은 자신이 몇 번째로 넘겼는지를 내부적으로 카운트한다(OS에 실제 현재 데스크톱을 물어보지 않음). 작은 항상-위 창에 다음 전환까지 남은 시간과, 앱이 스스로 센 데스크톱별 전환 횟수를 보여준다. 재시작하면 카운트는 초기화된다.
- **Appetite**: small (수일)
- **Trade-offs**: research.md에서 지적된 비공식 COM 인터페이스 의존이 전혀 없어 Windows 업데이트로 깨질 위험이 가장 낮다(problem.md의 "API 리스크" 전제와 정면으로 부딪히지 않음). 반면 사용자가 앱 밖에서 수동으로(`Ctrl+Win+←/→` 등) 데스크톱을 바꾸면 앱이 세는 "현재 위치"와 실제 OS 데스크톱이 어긋난다 — 즉 표시되는 전환 횟수는 실제가 아니라 "앱이 자기가 보낸 명령의 횟수"에 불과하다.
- **Rabbit holes**: 사용자가 수동 개입했을 때 동기화가 틀어지는 상황을 어디까지 감지/보정할지 — 여기 손대기 시작하면 금방 Option B 수준의 복잡도로 커진다. 선을 명확히 긋지 않으면 "small"이 깨진다.

### Option B — COM 래퍼 기반 정확한 로테이터 + 통계
- **Sketch**: research.md에서 찾은 비공식 COM 래퍼(예: mntone/VirtualDesktop, MScholtes/VirtualDesktop 계열)를 통해 실제 OS 가상 데스크톱 개수와 현재 인덱스를 직접 조회하고 전환도 그 인터페이스로 수행한다. 사용자가 수동으로 전환해도 앱이 정확히 인지한다. 데스크톱별 실제 전환 횟수를 로컬에 저장해 재시작 후에도 유지하고, 트레이 아이콘으로 일시정지/재개, 간격 조정 같은 제어를 제공한다.
- **Appetite**: medium (수 주)
- **Trade-offs**: intake.md가 원한 것(정확한 남은 시간, 정확한 데스크톱별 전환 횟수)을 문자 그대로 충족한다. 대가로 research.md의 "Evidence Against the Idea"에서 지목한 핵심 리스크 — 비공식·비문서화 CLSID/인터페이스에 의존해 Windows 빌드가 바뀔 때마다 깨질 수 있고, 빌드별 분기 코드를 유지보수해야 하는 부담 — 을 그대로 떠안는다.
- **Rabbit holes**: Windows 버전/빌드별 COM 인터페이스 분기 처리, 전환 이력 저장소 설계(파일 포맷, 마이그레이션), 트레이 UI/설정 화면이 "컨셉 수준"을 넘어 계속 커질 위험.

### Option C — 아무것도 새로 만들지 않고 기존 도구 활용 (VirtuaWin)
- **Sketch**: research.md에서 확인된 VirtuaWin(단축키/플러그인 기반 가상 데스크톱 관리자)을 그대로 쓰고, 필요하면 그 플러그인/스크립팅 기능으로 타이머 전환을 흉내 내며, 남은 시간·전환 횟수 표시는 별도 위젯(Rainmeter 등)으로 조합한다. 새 소프트웨어를 만들지 않는다.
- **Appetite**: small (설정/조합 작업만, 사실상 개발 비용은 거의 0)
- **Trade-offs**: 개발·유지보수 부담이 전혀 없고 검증된 도구를 쓴다는 장점이 있다. 하지만 결정적 문제가 있다 — VirtuaWin은 Windows 10/11의 네이티브 가상 데스크톱(Task View)이 아니라 자체 가상 화면 시스템을 구현한다. intake.md가 명시한 "Windows의 Virtual Desktop"과 다른 시스템으로 갈아타야 하며, 타이머 자동 전환과 데스크톱별 전환 횟수 통계는 VirtuaWin에 기본 내장되어 있지 않아 결국 스크립팅으로 직접 구현해야 한다.
- **Rabbit holes**: VirtuaWin이 네이티브 데스크톱을 대체한다는 점 때문에 다른 OS 기능(Task View, 창 스냅 등)과의 마찰이 생길 수 있고, "글루 스크립팅"이 커지면 사실상 Option A/B를 VirtuaWin 플러그인 형태로 재발명하는 셈이 된다.

## 추천

**Option A**를 추천한다. problem.md의 성공 지표가 아직 정성적·잠정 단계([NEEDS CLARIFICATION] 다수)이고, research.md의 "Evidence Against the Idea"가 지적한 핵심 리스크(비공식 API 불안정성)와 불확실한 수요를 감안하면, 가장 적은 비용으로 "정해진 간격 강제 전환이 실제로 도움이 되는가"라는 problem.md의 핵심 미검증 전제부터 검증하는 것이 합리적이다. Option B가 주는 정확도(진짜 OS 데스크톱 카운트)는 매력적이지만, 그 정확도를 사려면 research.md가 경고한 유지보수 리스크를 지금 당장 떠안아야 한다 — 아직 이 아이디어 자체가 가치가 있는지도 확정되지 않은 시점에는 과한 선투자다. Option C는 problem.md가 비목표로 못박은 "네이티브 OS 가상 데스크톱"이라는 전제를 깨뜨리므로 제외한다.

## 범위 밖 (추천 옵션 기준)

- 실제 OS 데스크톱 인덱스와 100% 일치가 보장되는 정확한 전환 횟수 (Option B 영역)
- 재시작 후에도 유지되는 전환 이력/설정 영속화
- 시스템 트레이 상주, Windows 시작 시 자동 실행
- 일시정지/재개, 간격 실시간 조정 등 런타임 제어 UI (최소 버전은 실행/종료만 가능하다고 가정)
- 데스크톱 생성·이름 변경·삭제 등 데스크톱 자체 관리 (problem.md 비목표에서 이미 제외)
- Windows 외 플랫폼 지원 (problem.md 비목표에서 이미 제외)

## 검증이 필요한 가정

- 사용자가 앱 실행 중에는 `Ctrl+Win+←/→`를 직접 누르지 않고 앱에 전환을 맡긴다는 가정 — 그렇지 않으면 카운트가 즉시 실제와 어긋난다.
- 사용자가 실행 시점에 알려주는 "총 데스크톱 개수"가 실제 존재하는 가상 데스크톱 수와 일치한다는 가정.
- 사용자의 Windows 빌드/환경에서 `Ctrl+Win+←/→` 키 입력 시뮬레이션이 다른 소프트웨어(타 유틸리티의 단축키 가로채기 등)에 막히지 않고 안정적으로 동작한다는 가정.
- problem.md의 핵심 전제 — "정해진 간격의 강제 전환"이 실제로 사용자에게 도움이 된다(방해가 아니라) — 는 아직 검증되지 않았고, 이 컨셉 전체가 그 가정 위에 서 있다.
